# Flatpak feasibility: raw research report

Generated 2026-09-13 by the deep-research workflow (5 angles, 22 sources, 25 claims verified by 3-way adversarial vote, 22 confirmed, 3 refuted). Companion to flatpak-plan.md, which is the distilled plan. Kept verbatim so the evidence and source URLs travel with the repo.

SUMMARY: Yes, a Flathub Flatpak of Drime Desktop is feasible, but not as a straight port: the sandbox cannot perform FUSE mounts itself (no setuid fusermount3, no CAP_SYS_ADMIN, user namespaces blocked, and a private slave mount namespace), and it cannot install or enable systemd user units in /usr/lib/systemd/user. Everything else ports cleanly: rclone >= 1.73 can be bundled as a Go module built offline in flatpak-builder (Deja Dup ships v1.75.1, Rclone Shuttle v1.73.1), org.gnome.Platform 50 supplies WebKitGTK 6.0, and Flathub takes over update distribution so the GitHub-Releases/PackageKit self-updater must simply be disabled in the Flatpak build. The FUSE mount is achievable through the accepted Deja Dup / Pika Backup / GNOME Builder pattern (a /app/bin/fusermount3 wrapper that forwards _FUSE_COMMFD to the host's fusermount3 via flatpak-spawn --host), but that requires --talk-name=org.freedesktop.Flatpak, which Flathub's linter treats as a sandbox-escape error granted only via a reviewed per-app exception; the same is true of --talk-name=org.freedesktop.systemd1 (precedents: Syncthing Tray, CTLDash). The recommended architecture is a tiered Flatpak: a zero-exception baseline that bundles rclone, runs bisync inside the sandbox against --filesystem=~/Drime:create with an internal scheduler autostarted through the Background portal (autostart + commandline), plus an optional FUSE-mount mode that activates only when the org.freedesktop.Flatpak exception is granted, while the RPM/DEB remain the full-integration path (persistent mount + systemd units). 

[0] (high, votes 3-0, 3-0) A FUSE mount cannot be performed from inside the Flatpak sandbox, and --device=all does not help: the sandbox runs with no capabilities, PR_SET_NO_NEW_PRIVS and nosuid mounts (so setuid fusermount3 cannot elevate), Flatpak's seccomp filter blocks clone(CLONE_NEWUSER)/clone3 (so the kernel's unprivileged-FUSE-in-userns path is closed), and Flathub's linter never grants --device=all. Even if a mount succeeded, bubblewrap marks the sandbox root MS_SLAVE and pivot_roots into a private tmpfs, so mounts created inside the sandbox never propagate to the host, Nautilus, or other apps. 
  EVIDENCE: Wiki text verbatim: '/ is a private tmpfs not visible anywhere else. [1] (high, votes 3-0, 3-0, 3-0) The accepted workaround for FUSE inside a Flatpak is to install a shell wrapper as /app/bin/fusermount3 that execs `flatpak-spawn --host fusermount3` while forwarding the _FUSE_COMMFD socket (--env=_FUSE_COMMFD=N --forward-fd=N) and any /dev/fd/N mountpoint argument; the host fusermount3 opens /dev/fuse and passes the fd back over SCM_RIGHTS, so rclone's FUSE server runs inside the sandbox while the mount itself is created in the host mount namespace at the requested path (hence visible to Nautilus and other apps, and propagated back into the sandbox because the sandbox root is a slave of the host). Both rclone `mount` (bazil.org/fuse) and `mount2` (hanwen/go-fuse) exec fusermount3 with this protocol. Deja Dup (org.gnome.DejaDup, Flathub, runtime 50) uses exactly this with `--talk-name=org.freedesktop.Flatpak` plus `--filesystem=xdg-run/deja-dup:create`, noting no fusermount portal exists yet (xdg-desktop-portal issue #695); GNOME Builder and Pika Backup use the same wrapper. RClone Manager ships the wrapper too but its manifest omits the org.freedesktop.Flatpak talk-name, so its mount path likely does not work out of the box (the earlier claim that it 'makes mounts work' was refuted 0-3). 
  EVIDENCE: Wrapper (last commit 2025-12-07) verbatim: 'FD_ARGS+=(--env=_FUSE_COMMFD=${_FUSE_COMMFD}) ... --forward-fd=${_FUSE_COMMFD} ... if [[ $ARG =~ ^/dev/fd/[0-9]+$ ]] ... exec flatpak-spawn --host ${FD_ARGS[@]} fusermount3 $@'. Deja Dup manifest verbatim: '# Mounting via the host's fusermount ... - --filesystem=xdg-run/deja-dup:create - --talk-name=org.freedesktop.Flatpak'. Verifier traced libfuse lib/mount.c / util/fusermount.c socketpair + SCM_RIGHTS handoff and bazil mount_linux.go line 76 / go-fuse mount_linux.go line 145. The 'visible to Nautilus / propagates back into the sandbox' consequence is an inference from the MS_SLAVE design (host->sandbox propagation allowed) and Deja Dup reading the mounted path from inside the sandbox; it was not separately tested. Claims [0], [1], [2] merged, all 3-0.

[3] (high, votes 3-0, 3-0, 3-0, 3-0, 2-1, 2-1) A Flatpak can control existing systemd user units over the session bus with --talk-name=org.freedesktop.systemd1 (Manager at /org/freedesktop/systemd1: StartUnit/StopUnit/RestartUnit/GetUnit; verified empirically from inside a sandbox on this Fedora 44 host, and ServiceUnknown without the talk-name), and can even run rclone as a supervised transient unit with StartTransientUnit (no unit file on disk) or enable an out-of-tree unit file by absolute path with EnableUnitFiles/LinkUnitFiles. [4] (high, votes 3-0, 3-0) The sandbox-native substitute for a systemd user unit is the Background portal's RequestBackground with `autostart: true` and a `commandline` array, which writes ~/.config/autostart/<app-id>.desktop with Exec=`flatpak run --command=<argv0> <app-id> <args>`; this lets the app register a headless 'drime-desktop --daemon' mode that runs bisync on an internal 15-minute timer (and, if the FUSE exception is granted, holds the mount) at login. It is not a service model: the portal (interface v2, still only RequestBackground + SetStatus as of 1.22.1) offers no supervision, restart-on-failure, timers, or on-demand start; the user/desktop may deny the permission (ASK dialog on GNOME/KDE); omitting `autostart` deletes any existing autostart entry; and the commandline can only launch in-sandbox commands, never host binaries. Consequently the original claim that the Background portal is a drop-in substitute for enabling a systemd unit was refuted (0-3). 
  EVIDENCE: Spec verbatim: 'autostart (b) true if the app also wants to be started automatically at login. commandline (as) Commandline to use when autostarting at login. If this is not specified, the Exec key from the desktop file will be used.' Maintainer GeorgesStavracas on #899 (2022-10-21): 'There is no standard way to spawn an application as a service, so ... we cannot currently just bind background running to autostart.' Verifier read background.c: handle_request_background -> enable_autostart_sync -> rewrite_commandline emitting `flatpak run --command=...`. Claims [9] and [17] merged, both 3-0.

[8] (medium, votes n/a (synthesis)) Verdict and recommended architecture: FEASIBLE with a tiered design. Tier 0 (no linter exceptions, works on every distro): bundle rclone, run `rclone bisync` inside the sandbox against ~/Drime with an in-process 15-minute scheduler in a headless `--daemon` mode registered through the Background portal (autostart + commandline); finish-args: --socket=wayland, --socket=fallback-x11, --device=dri, --share=ipc, --share=network, --filesystem=~/Drime:create, --talk-name=org.freedesktop.Notifications, --talk-name=org.freedesktop.secrets (if the token lives in the keyring), --talk-name=org.kde.StatusNotifierWatcher (if a tray icon is used).
